# ADR-0008: Идемпотентность операций записи и обработки событий

- **Status:** Proposed
- **Date:** 2026-09-30
- **Stage:** 1
- **Related:** requirements §4.4, §4.5; ADR-0003, ADR-0005

## Problem

Штатные retry (сетевой сбой клиента, повтор после timeout, повторная доставка события из outbox) не должны
создавать дублей: второго обращения, второго сообщения, второго AI-запроса, второго уведомления (§4.4,
§4.5).

## Constraints

- Клиент может не узнать, закоммитилась ли его операция.
- Outbox даёт at-least-once доставку (ADR-0003).
- Дубликаты отбрасываются в БД, без распределённых блокировок.

## Options

1. Не защищаться, полагаться на то, что retry редки.
2. Общая таблица idempotency keys для всех HTTP-запросов с сохранением ответов.
3. Естественные уникальные ключи на уровне сущностей плюс inbox для обработчиков событий.

## Decision

Вариант 3.

| Операция | Ключ идемпотентности |
|---|---|
| Создание обращения | `Idempotency-Key` → `UNIQUE (CustomerId, IdempotencyKey)` |
| Отправка сообщения | `Idempotency-Key` → `UNIQUE (ConversationId, IdempotencyKey)` |
| Обработчик integration event | Inbox: `UNIQUE (HandlerName, EventId)` в той же транзакции, что и эффект обработчика |
| AI-запрос | `UNIQUE (ConversationId, Kind, InputUpToSeq)` |
| Уведомление | `UNIQUE (SourceEventId)` |
| Audit | `UNIQUE (SourceEventId)` |

При повторе с тем же ключом API возвращает уже созданный ресурс.

## Trade-offs

**Плюсы:**
- Идемпотентность гарантирует ограничение уникальности в БД, без отдельной инфраструктуры.
- Каждая защита привязана к своей сущности и понятна из схемы.

**Минусы:**
- Клиенты обязаны генерировать и повторно передавать ключ.
- Повтор с тем же ключом, но другим телом запроса не обнаруживается (хэш тела не хранится).
- Индексы уникальности увеличивают объём хранения и стоимость записи.
