# ADR-0008: Идемпотентность операций записи и обработки событий

- **Status:** Proposed
- **Date:** 2026-09-30
- **Stage:** 1
- **Related:** requirements §4.4, §4.5; ADR-0003, ADR-0005

## Problem

Штатные retry (сетевой сбой клиента, повтор после timeout, повторная доставка события из outbox) не должны
создавать дублей: второго обращения, второго сообщения, второго AI-запроса, второго уведомления (§4.4,
§4.5).

## Constraints

- Клиент может не узнать, закоммитилась ли его операция.
- Outbox даёт at-least-once доставку (ADR-0003).
- Дубликаты отбрасываются в БД, без распределённых блокировок.

## Options

1. Не защищаться, полагаться на то, что retry редки.
2. Общая таблица idempotency keys для всех HTTP-запросов с сохранением ответов.
3. Естественные уникальные ключи на уровне сущностей плюс inbox для обработчиков событий.

## Decision

Вариант 3.

| Операция | Ключ идемпотентности |
|---|---|
| Создание обращения | **Заменено [ADR-0014](0014-idempotency-keys-table.md).** Было: `Idempotency-Key` → `UNIQUE (CustomerId, IdempotencyKey)` |
| Отправка сообщения | **Заменено [ADR-0014](0014-idempotency-keys-table.md).** Было: `Idempotency-Key` → `UNIQUE (ConversationId, AuthorId, IdempotencyKey)` |
| Обработчик integration event | Inbox: `UNIQUE (HandlerName, EventId)` в той же транзакции, что и эффект обработчика |
| AI-запрос | `UNIQUE (ConversationId, Kind, InputUpToSeq)`. Повтор после `Failed` переиспользует ту же запись (ADR-0009) |
| Уведомление | `UNIQUE (SourceEventId)`. `NotificationId` передаётся провайдеру как его idempotency key |
| Audit | `UNIQUE (SourceEventId)` |

> Для создания обращения и отправки сообщения действует [ADR-0014](0014-idempotency-keys-table.md): ключи
> хранятся в отдельной таблице модуля, а не в сущностях. Текст ниже — исходное решение, сохранено для истории.

При повторе с тем же ключом API возвращает уже созданный ресурс того же автора.

Порядок проверки при создании обращения и отправке сообщения:
1. Поиск существующей записи по ключу. Если найдена — вернуть её, ничего не изменяя (и не расходуя лимиты
   ADR-0012).
2. Иначе — обычная транзакция команды.
3. Если INSERT нарушил ограничение уникальности (конкурентный повтор прошёл шаг 1 одновременно), транзакция
   откатывается целиком, включая изменение `Conversation`, и API возвращает запись, созданную первым
   запросом.

`AuthorId` входит в ключ сообщения, чтобы повтор чужого ключа не возвращал сообщение другого автора.

## Trade-offs

**Плюсы:**
- Идемпотентность гарантирует ограничение уникальности в БД, без отдельной инфраструктуры.
- Каждая защита привязана к своей сущности и понятна из схемы.

**Минусы:**
- Клиенты обязаны генерировать и повторно передавать ключ.
- Повтор с тем же ключом, но другим телом запроса не обнаруживается (хэш тела не хранится).
- Индексы уникальности увеличивают объём хранения и стоимость записи.
