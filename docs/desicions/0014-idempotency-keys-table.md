# ADR-0014: Ключи идемпотентности HTTP-команд в отдельной таблице модуля

- **Status:** Proposed
- **Date:** 2026-10-07
- **Stage:** 1
- **Related:** requirements §4.4, §4.5, §4.7, §4.8, §5.3, §13; domain-model §3.3, §12; ADR-0002, ADR-0003,
  ADR-0004, ADR-0008, ADR-0012, ADR-0013

Заменяет в ADR-0008 решения для создания обращения и отправки сообщения. Остальные решения ADR-0008 (inbox,
AI-запросы, уведомления, audit) не меняются.

## Problem

ADR-0008 хранит `Idempotency-Key` создания обращения и отправки сообщения в самих сущностях:
`UNIQUE (CustomerId, IdempotencyKey)` на `Conversation` и `UNIQUE (ConversationId, AuthorId, IdempotencyKey)` на
`Message`. Ключ защищает от повторных HTTP-запросов и не имеет бизнес-смысла, поэтому такое хранение:
- переносит транспортную деталь в Domain (architecture.md §11, ADR-0013);
- хранит ключ, нужный минуты, вместе с данными ~3 года (§4.8);
- добавляет на `messages` (~700k строк в сутки, §5.3) колонку и уникальный индекс. Уникальный индекс
  партиционированной таблицы в PostgreSQL обязан включать ключ партиционирования, поэтому этот индекс мешает
  будущему партиционированию `messages` (domain-model §12);
- не обнаруживает повтор с тем же ключом, но другим телом запроса.

## Constraints

- Обращения и сообщения не должны дублироваться из-за штатных retry (§4.4, §4.5).
- Защита от дублей — в той же транзакции, что и бизнес-запись, без распределённых блокировок.
- Повтор возвращает уже созданный ресурс и не расходует лимиты (ADR-0012).
- Модуль пишет только в свою схему (ADR-0002).
- Без новой инфраструктуры (§13).

## Options

1. **Поле агрегата** (решение ADR-0008).
2. **Колонка в таблице сущности, но не в агрегате** (persistence-деталь, shadow property).
3. **Отдельная таблица ключей в схеме модуля**, запись в той же транзакции, что и бизнес-данные.
4. **Общее хранилище HTTP-ответов** (middleware), запись отдельно от бизнес-транзакции.

## Decision

Вариант 3.

**Семантика.** Ключ принадлежит HTTP-команде: один запрос — один ключ. Команда с одним ключом создаёт ресурс не
более одного раза. Записывается только успешно закоммиченный результат: если команда завершилась ошибкой,
транзакция откатывается вместе с ключом, и повтор выполняет команду заново. Ресурсы, созданные той же командой
(первое сообщение при создании обращения), своих ключей не имеют.

**Таблица** в схеме каждого модуля с идемпотентными командами (`conversations.idempotency_keys`):

| Колонка | Тип | |
|---|---|---|
| `caller_id` | `uuid` | PK. Аутентифицированный пользователь |
| `key` | `uuid` | PK. Значение `Idempotency-Key` |
| `operation` | `text` | PK. Имя команды: `OpenConversation`, `PostMessage` |
| `request_hash` | `bytea` | SHA-256 входа команды |
| `resource_id` | `uuid` | Созданный ресурс |
| `created_at` | `timestamptz` | Индекс для очистки |

**Scope** — `(caller_id, key, operation)`. Ключи разных пользователей и разных операций не пересекаются, чужой
ключ не возвращает чужой ресурс. Целевой ресурс (обращение для `PostMessage`) входит в request hash, а не в
scope. `Idempotency-Key` обязателен и должен быть UUID **[Assumption]**, иначе endpoint отвечает `400`.

**Request hash** — SHA-256 полей команды в фиксированном порядке, каждое поле с префиксом длины, UTF-8.
Хешируются значения в том виде, в каком пришли, до нормализации. `caller_id`, `key` и заголовки не входят.
- `OpenConversation`: `subject`, `firstMessage`.
- `PostMessage`: `conversationId`, `body`.

**Порядок обработки:**
1. Поиск по scope. Найдено и hash совпал — `200` и текущее состояние ресурса, лимиты не проверяются. Найдено и
   hash отличается — `422 Unprocessable Content`.
2. Application создаёт id ресурса.
3. Транзакция: **первой командой** вставляется строка ключа, затем блокировки и лимиты (ADR-0012, ADR-0004),
   агрегат, бизнес-данные и outbox.
4. Нарушение первичного ключа — откат всей транзакции и повтор шага 1.

Ключ вставляется первым, потому что конкурентный повтор ждёт на этой вставке, пока первая транзакция не
завершится, и не выполняет бизнес-проверки. Иначе повтор запроса, создавшего десятое обращение за сутки или
тысячное сообщение, получил бы `429` или `409` вместо созданного ресурса. Ключ всегда блокируется раньше
advisory lock клиента и строки `Conversation`, поэтому порядок захвата блокировок одинаков во всех командах.

| Конкурентный сценарий | Результат |
|---|---|
| Тот же ключ, то же тело | Второй запрос ждёт, получает нарушение PK, находит ресурс первого — `200` |
| Тот же ключ, другое тело | Нарушение PK, hash отличается — `422` |
| Первая транзакция откатилась | Второй запрос выполняется как обычно |

**Ответ на повтор** — текущее состояние ресурса по `resource_id`, а не сохранённый первый ответ.

**Retention.** Ключи хранятся не меньше 48 часов **[Assumption]**. Scheduler Worker удаляет более старые записи
пачками, как outbox и inbox. Поиск не фильтрует истёкшие записи: пока запись не удалена, она защищает. После
удаления повтор с тем же ключом создаст новый ресурс.

**Реализация.** Порт хранилища ключей и вычисление hash — в BuildingBlocks, таблица — в схеме каждого модуля.
Вставка ключа выполняется немедленно, а не откладывается до сохранения остальных изменений.

## Trade-offs

**Плюсы:**
- Domain не знает о ключах идемпотентности.
- Ключи не хранятся 3 года, таблица маленькая: ~800k записей в сутки, при 48 часах порядка сотен мегабайт.
- С `messages` уходит уникальный индекс, мешающий партиционированию.
- Повтор ключа с другим телом обнаруживается.
- Конкурентный повтор не получает ошибку лимита вместо созданного ресурса.

**Минусы:**
- Лишний INSERT в транзакции каждой идемпотентной команды.
- После удаления ключа защита от повтора пропадает.
- Ответ на ошибочный запрос не запоминается: повтор выполняет команду заново.
- Конкурентный повтор ждёт завершения первой транзакции (ограничено `lock_timeout`).
- Короткий in-memory лимит 1 msg/s (ADR-0012) стоит до проверки ключа, поэтому быстрый повтор сообщения может
  получить `429`. Ресурс не дублируется, повтор после `Retry-After` вернёт созданное сообщение.
- Вариант 1 отвергнут: транспортная деталь в домене, хранение и индекс на 3 года. Вариант 2 убирает ключ из
  домена, но оставляет хранение и индекс на `messages`. Вариант 4 отвергнут в ADR-0008: запись вне
  бизнес-транзакции даёт гонки, а запись внутри неё сводится к варианту 3.
