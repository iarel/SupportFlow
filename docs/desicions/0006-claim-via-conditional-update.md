# ADR-0006: Текущий Assignee в Conversation, claim через условный UPDATE

- **Status:** Proposed
- **Date:** 2026-09-30
- **Stage:** 1
- **Related:** requirements FR-006, FR-012, FR-013, §4.5; domain-model §3.2; ADR-0007

## Problem

Два сотрудника не должны одновременно успешно взять одно обращение (§4.5). Нужно выбрать, где хранится
текущее назначение и как обеспечивается его единственность.

## Constraints

- Операция интерактивная: p95 ≤ 200 ms.
- История назначений нужна для отчётов (нагрузка, статистика).
- Несколько instances API: in-memory блокировки не работают.

## Options

1. Назначения хранятся только в таблице `Assignment`, активное назначение уникально по partial unique
   index.
2. Пессимистическая блокировка (`SELECT … FOR UPDATE`) с последующей проверкой и записью.
3. `AssigneeId` хранится в `Conversation`, claim выполняется условным UPDATE:
   `WHERE status = 'New' AND assignee_id IS NULL`. `AssignmentHistory` — append-only журнал.

## Decision

Вариант 3.
- Claim: условный UPDATE. Если затронуто 0 строк, ответ `409 Conflict`.
- Assign/Reassign от Supervisor: optimistic concurrency по `Version` (ADR-0007).
- Каждое изменение назначения пишет запись в `AssignmentHistory` в той же транзакции.

## Trade-offs

**Плюсы:**
- Один round-trip, никаких удерживаемых блокировок. Гонку разрешает атомарность UPDATE в PostgreSQL.
- Инвариант «не больше одного Assignee» следует из схемы, а не из дополнительных индексов.

**Минусы:**
- Текущее назначение и история хранятся в двух местах, и история может разойтись с текущим состоянием,
  если писать её вне транзакции. Поэтому она пишется строго в той же транзакции.
- Проверка «Agent активен и состоит в команде» выполняется до UPDATE через контракт Support Organization.
  Редкая гонка с изменением состава команды допускается.
