# ADR-0001: Модульный монолит — API и Worker, одна PostgreSQL

- **Status:** Proposed
- **Date:** 2026-09-30
- **Stage:** 1
- **Related:** requirements §4.1, §4.2, §4.3, §12.1, §12.2; ADR-0002, ADR-0003

## Problem

Нужно выбрать форму развёртывания начальной системы. В системе есть два принципиально разных типа
нагрузки:
- интерактивные операции с целевыми p95 ≤ 200–300 ms (§4.1);
- фоновые операции: AI-вызовы до 10 s, отправка уведомлений, доставка событий. Они медленные, зависят от
  ненадёжных внешних систем и приходят пачками.

## Constraints

- Требования фиксируют модульный монолит и одну PostgreSQL (§1, §12).
- Отдельные сервисы не выделяются заранее без подтверждённой необходимости (§4.2).
- Отказ отдельного instance или некритичной внешней зависимости не должен ломать основной поток (§4.3).
- AI processing и notifications названы кандидатами на независимое масштабирование (§4.2).

## Options

1. **Один процесс.** Фоновая работа выполняется как `IHostedService` внутри API.
2. **Один код, два host-процесса.** API обслуживает HTTP, Worker — фоновую обработку. Обе сборки состоят из
   тех же модулей.
3. **Микросервисы по bounded contexts.**

## Decision

Вариант 2. Система — модульный монолит с двумя entrypoint:
- **SupportFlow API**: stateless HTTP, все команды и запросы;
- **SupportFlow Worker**: outbox dispatcher, обработчики событий, AI jobs, отправка уведомлений,
  периодические задачи.

Оба процесса работают с одной PostgreSQL и не вызывают друг друга напрямую. Развёртывание: Docker, не меньше
2 instances каждого процесса, один регион.

## Trade-offs

**Плюсы:**
- Медленная и ненадёжная фоновая работа не забирает thread pool и соединения с БД у интерактивных запросов.
- API и Worker масштабируются независимо, числом instances.
- Остаются все преимущества монолита: одна кодовая база, локальные транзакции, простая отладка.
- Вариант 3 отвергнут: он зафиксировал бы границы модулей до появления данных о реальной нагрузке (§12.1).

**Минусы:**
- Нужно поддерживать два процесса в развёртывании.
- Модули Worker и API делят одну БД и конкурируют за её ресурсы.
- Единственный instance PostgreSQL — single point of failure всей системы.
