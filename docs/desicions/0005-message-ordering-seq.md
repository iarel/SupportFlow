# ADR-0005: Порядок сообщений через per-conversation `Seq`

- **Status:** Proposed
- **Date:** 2026-09-30
- **Stage:** 1
- **Related:** requirements §4.6; domain-model §3.3; ADR-0004

## Problem

Сообщения внутри обращения должны иметь однозначный порядок, в том числе при одновременной отправке
клиентом и агентом (§4.6).

## Constraints

- Несколько stateless instances API, часы которых не синхронизированы.
- Порядок должен быть стабильным и одинаковым для всех читателей.
- Пагинация истории (API не возвращает неограниченную историю, §10).

## Options

1. Сортировка по `CreatedAt`.
2. Глобальный `bigserial` / identity.
3. Per-conversation `Seq`, выдаваемый агрегатом `Conversation` (`LastMessageSeq + 1`) в транзакции
   отправки.

## Decision

Вариант 3. Порядок отображения определяется только `Seq`.
Уникальность `(ConversationId, Seq)` обеспечивается ограничением в БД.
Правило для пользователя: **сообщения упорядочены по порядку коммита их регистрации в обращении**.

## Trade-offs

**Плюсы:**
- Порядок однозначен и плотный (1, 2, 3, … без пропусков).
- Клиент может запрашивать сообщения после `Seq = N`, что даёт простую keyset-пагинацию и polling новых
  сообщений.

**Минусы:**
- Конкурентные отправки в одно обращение сериализуются на строке `Conversation` (см. ADR-0004).
- Вариант 1 отвергнут: одинаковые timestamps и рассинхронизация часов. Вариант 2 отвергнут: `bigserial`
  монотонен только по порядку выдачи значений, а не по порядку коммита, и даёт пропуски после rollback.
