# ADR-0012: Стратегия rate limiting

- **Status:** Proposed
- **Date:** 2026-09-30
- **Stage:** 1
- **Related:** requirements §4.7, §6; domain-model §3.6; ADR-0001

## Problem

Нужно ограничить интенсивность пользовательских операций (§4.7):
- не больше 10 новых обращений от Customer в сутки;
- не больше 1 сообщения в секунду от Customer;
- дополнительно лимиты на API requests и AI requests.

API работает в нескольких stateless instances.

## Constraints

- Лимиты — защита от нагрузки и роста данных, а не бизнес-инвариант агрегата (domain-model §3.6).
- Новая инфраструктура добавляется только при обосновании (§13).

## Options

1. Все лимиты в памяти instance (ASP.NET Core `RateLimiter`).
2. Все лимиты через PostgreSQL (счётчики или окна в таблице).
3. Комбинация: длинное окно (сутки) проверяется точно запросом в БД, короткие окна (секунда) — приблизительно
   в памяти instance.

## Decision

Вариант 3.
- **10 обращений в сутки:** в транзакции создания обращения берётся
  `pg_advisory_xact_lock(hash(customer_id))`, затем выполняется `COUNT` по индексу
  `(customer_id, created_at)`. Без блокировки при Read Committed два параллельных запроса оба увидели бы 9 и
  оба создали обращение. Блокировка сериализует только создания обращений одного Customer и снимается при
  COMMIT. Идемпотентный повтор (ADR-0008) возвращает существующее обращение до проверки лимита.
- **1 сообщение в секунду и общий лимит API requests:** `RateLimiter` в памяти instance, ключ — пользователь.
- **AI requests:** не больше N запросов Summary/ReplyDraft/Retry на сотрудника в час **[Assumption]**.
  Проверяется `COUNT` по `ai.suggestions` (индекс `(requested_by_id, requested_at)`), без отдельной таблицы
  счётчиков. Небольшое превышение при гонке допустимо: это защита от нагрузки, а не бизнес-инвариант.
  Плюс ограничение параллелизма вызовов AI Provider в Worker (ADR-0003).
- Превышение → `429 Too Many Requests` с `Retry-After`.

## Trade-offs

**Плюсы:**
- Нет новой инфраструктуры.
- Суточный лимит точный. Короткие лимиты не нагружают БД.

**Минусы:**
- Короткие лимиты приблизительные: при N instances API фактический лимит до N msg/s на пользователя.
- Состояние in-memory limiter теряется при перезапуске instance.
- Суточная проверка добавляет advisory lock и запрос в транзакцию создания обращения.
