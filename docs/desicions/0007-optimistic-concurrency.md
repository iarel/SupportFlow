# ADR-0007: Optimistic concurrency — `Version` и ETag

- **Status:** Proposed
- **Date:** 2026-09-30
- **Stage:** 1
- **Related:** requirements §4.5; domain-model §11; ADR-0006

## Problem

Конкурентные изменения состояния обращения (статус, категория, приоритет, переназначение) не должны
незаметно затирать друг друга (§4.5). Пример: Supervisor переназначает обращение, пока Agent меняет его
приоритет на основе устаревших данных.

## Constraints

- Конфликты редки: с обращением обычно работает один Agent.
- Stateless API, между запросами сессий нет.
- Пользователь должен узнать, что действовал на основе устаревших данных.

## Options

1. Last write wins.
2. Пессимистическая блокировка на время редактирования.
3. Optimistic concurrency: `Version` в агрегате, передаётся клиенту как `ETag` и возвращается в `If-Match`.

## Decision

Вариант 3.
- `Conversation.Version` увеличивается при каждом изменении.
- Сохранение: `UPDATE … WHERE id = @id AND version = @expected`, где `@expected` — версия из `If-Match`.
  Инварианты проверяет агрегат до UPDATE (ADR-0013).
- Команды изменения требуют `If-Match`:
  - заголовок отсутствует → `428 Precondition Required`;
  - версия не совпадает → `412 Precondition Failed`, клиент перечитывает состояние.
- Claim не требует `If-Match`: ожидаемая версия — загруженная сервером, конфликт → `409 Conflict`
  (ADR-0006).
- Отправка сообщения не требует `If-Match`: сообщения не конфликтуют, они упорядочиваются блокировкой строки
  `Conversation` (ADR-0004, ADR-0005).

## Trade-offs

**Плюсы:**
- Нет удерживаемых блокировок, подходит для stateless API.
- Конфликты обнаруживаются явно.

**Минусы:**
- Клиент должен обрабатывать 412 и перечитывать данные.
- Сообщение увеличивает `Version` (меняются счётчики), поэтому новое сообщение клиента инвалидирует ETag
  агента. Это ожидаемо: агент должен видеть актуальную переписку перед сменой статуса.
