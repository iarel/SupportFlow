# ADR-0013: Внутреннее устройство модуля — DDD, Onion/Clean, Ports & Adapters

- **Status:** Proposed
- **Date:** 2026-10-06
- **Stage:** 1
- **Related:** requirements §12.1, §13, §16; domain-model §0; ADR-0002, ADR-0004, ADR-0006

## Problem

ADR-0002 задаёт границы между модулями, но не задаёт устройство модуля изнутри. Без общего правила модули
расходятся по стилю, бизнес-правила оказываются в endpoints, SQL или обработчиках событий, а доменная
модель превращается в анемичные структуры данных.

## Constraints

- Модули должны иметь явные границы и минимальную связанность (§12.1).
- Core domain (Conversations) содержит инварианты конкурентного доступа (§4.5), которые должны проверяться
  в одном месте.
- AI и Notification Provider — ненадёжные внешние зависимости, которые нужно изолировать и заменять (§13).
- ADR-0002 отверг разбиение модуля на 4+ проекта как избыточное.

## Options

1. Глобальная слоистая структура `Controllers → Services → Repositories` для всей системы.
2. Слои внутри каждого модуля (Domain / Application / Infrastructure + inbound adapters) как папки одного
   проекта. Зависимости направлены к домену, внешние системы доступны через порты.
3. То же, что вариант 2, но каждый слой — отдельный проект.
4. Vertical slices без доменного слоя (transaction script на use case).

## Decision

Вариант 2. Подробные правила — в [architecture.md](../architecture/architecture.md).
- Слои — папки внутри проекта модуля. Публичный контракт — отдельный проект `*.Contracts`.
- Инварианты агрегатов проверяются в Domain. БД обеспечивает атомарность сохранения и обнаружение
  конфликтов (`Version`, блокировка строки), но не заменяет доменные проверки SQL-условиями.
- Команды проходят через агрегаты. Запросы и отчёты читают данные напрямую, минуя Domain (CQS).
- Модуль без инвариантов (Reporting) не имеет Domain-слоя.
- Направление зависимостей проверяется архитектурными тестами.

## Trade-offs

**Плюсы:**
- Бизнес-правила находятся в одном месте и тестируются без БД и HTTP.
- Внешние системы заменяются через адаптеры.
- Граница модуля остаётся главной. Слои не превращаются в глобальную структуру.

**Минусы:**
- Дисциплину внутри одного проекта поддерживают архитектурные тесты, а не компилятор.
- Загрузка агрегата перед изменением даёт два round-trip к БД вместо одного условного UPDATE (ADR-0006).
- Вариант 1 отвергнут: размывает границы модулей. Вариант 3 отвергнут в ADR-0002. Вариант 4 отвергнут для
  Conversations: инварианты конкурентного доступа распределились бы по обработчикам; для простых модулей
  он фактически допускается принципом прагматизма.
