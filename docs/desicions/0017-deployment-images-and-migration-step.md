# ADR-0017: Развёртывание: два образа, миграции отдельным шагом

- **Status:** Proposed
- **Date:** 2026-10-10
- **Stage:** 1
- **Related:** ADR-0001, ADR-0002, requirements §4.3, §13

## Problem

Нужно определить, как API и Worker поставляются и как применяются миграции семи модулей вне Development.
Сейчас миграции применяет API при старте только в Development.

## Constraints

- Не меньше 2 instances API и Worker, отказ одного не прерывает обслуживание (§4.3, ADR-0001).
- Kubernetes и другая инфраструктура — только при конкретном обосновании (§13); его пока нет.
- У каждого модуля свой DbContext, схема и таблица истории миграций (ADR-0002).
- Во время обновления старые instances работают с уже мигрированной схемой.

## Options

1. Миграции при старте каждого instance. Просто, но instances конкурируют за миграцию, старт ждёт DDL,
   приложению нужны права на DDL.
2. EF migration bundle на каждый DbContext. Отдельные исполняемые файлы, семь артефактов и SDK-tooling в сборке.
3. Отдельный шаг `migrate` в образе API, запускаемый один раз перед новой версией.

## Decision

- Два образа: `supportflow-api` и `supportflow-worker`, multi-stage сборка, runtime-образ ASP.NET chiseled,
  процесс без root. Конфигурация — переменные окружения (`ConnectionStrings__SupportFlow`, `OTEL_*`, настройки JWT).
- Вариант 3: `supportflow-api migrate` применяет миграции всех модулей и завершается. Шаг выполняется до
  запуска новой версии; ошибка останавливает развёртывание. API и Worker вне Development схему не меняют.
- Миграции обратно совместимы с предыдущей версией приложения (expand/contract): удаление и переименование
  колонок — отдельным релизом после того, как старый код больше не работает.
- Оркестратор не выбирается: от него требуются перезапуск, пробы `/health/live` и `/health/ready`, rolling
  update, корректная остановка (SIGTERM) и запуск разового шага перед обновлением. Для локального
  production-like запуска — `deploy/docker-compose.yml`.

## Trade-offs

**Плюсы:**
- Миграция выполняется один раз и не гоняется между instances; старт instance не ждёт DDL.
- Приложению можно выдать роль без прав на DDL.
- Выбор оркестратора отложен до обоснования (§13).

**Минусы:**
- Развёртывание из двух шагов.
- Правило expand/contract усложняет изменения схемы.
- Образ API содержит команду, нужную только при развёртывании.
