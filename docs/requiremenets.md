# SupportFlow — Требования

## 1. Обзор продукта

**SupportFlow** — платформа для обработки обращений клиентов в службу поддержки.

Система позволяет клиентам создавать обращения и обмениваться сообщениями с сотрудниками поддержки. Сотрудники поддержки обрабатывают обращения, а руководители управляют распределением нагрузки и контролируют работу поддержки.

Система также предоставляет AI-инструменты для классификации обращений, предложения приоритета, формирования summary и генерации рекомендуемого ответа.

Система развивается от простого MVP к production-like highload-системе.

Начальная реализация намеренно использует **модульный монолит и одну PostgreSQL database**. При этом архитектура MVP должна учитывать потенциальный рост нагрузки, объёма данных и требований к доступности, чтобы дальнейшее масштабирование было эволюционным, а не требовало полного переписывания системы.

---

# 2. Акторы

## 2.1 Customer

Клиент взаимодействует со службой поддержки через обращения.

Основные возможности:

* создать обращение;
* отправить сообщение;
* просматривать свои обращения;
* просматривать историю сообщений.

## 2.2 Support Agent

Сотрудник поддержки обрабатывает обращения клиентов.

Основные возможности:

* просматривать назначенные ему обращения;
* взять свободное обращение в работу;
* отправить ответ клиенту;
* изменить статус обращения;
* изменить категорию обращения;
* изменить приоритет обращения.

## 2.3 Supervisor

Руководитель поддержки управляет процессом обработки обращений.

Основные возможности:

* просматривать обращения в своей зоне ответственности;
* назначать обращения сотрудникам поддержки;
* переназначать обращения между сотрудниками;
* просматривать текущую нагрузку сотрудников;
* просматривать метрики и отчёты.

## 2.4 AI

AI предоставляет сотрудникам поддержки рекомендации и вспомогательные функции.

Основные возможности:

* классифицировать обращение;
* предложить приоритет обращения;
* сформировать summary обращения;
* предложить ответ клиенту.

AI не принимает окончательные бизнес-решения самостоятельно. Итоговое решение и отправка ответа остаются за Support Agent.

## 2.5 External Systems

Внешние системы предоставляют функциональность, не относящуюся непосредственно к основному домену SupportFlow.

На начальном этапе предусматривается:

* **Notification Provider** — отправка уведомлений клиентам о значимых событиях обращения.

Дополнительные внешние интеграции находятся за пределами MVP.

# 3. Функциональные требования

**FR-003** — Система должна позволять Customer просматривать свои обращения.

**FR-004** — Система должна позволять Customer просматривать историю сообщений в рамках обращения.

## 3.2 Support Agent

**FR-005** — Система должна позволять Support Agent просматривать назначенные ему обращения.

**FR-006** — Система должна позволять Support Agent брать в работу свободное обращение.

**FR-007** — Система должна позволять Support Agent отправлять сообщения в рамках обращения.

**FR-008** — Система должна позволять Support Agent изменять статус обращения.

**FR-009** — Система должна позволять Support Agent изменять категорию обращения.

**FR-010** — Система должна позволять Support Agent изменять приоритет обращения.

## 3.3 Supervisor

**FR-011** — Система должна позволять Supervisor просматривать доступные ему обращения.

**FR-012** — Система должна позволять Supervisor назначать обращение Support Agent.

**FR-013** — Система должна позволять Supervisor переназначать обращение между Support Agent.

**FR-016** — Система должна уметь классифицировать обращение с использованием AI.

**FR-017** — Система должна уметь формировать предложение по приоритету обращения с использованием AI.

**FR-018** — Система должна уметь формировать summary обращения.

**FR-019** — Система должна уметь формировать рекомендуемый ответ для Support Agent.

**FR-020** — AI-рекомендации должны быть явно отличимы от решений, принятых Support Agent.

## 3.5 Уведомления

**FR-021** — Система должна иметь возможность отправлять клиенту уведомления о значимых событиях обращения через внешний Notification Provider.

# 4. Нефункциональные требования

## 4.1 Производительность

Система должна обеспечивать предсказуемое время ответа для интерактивных операций.

При оценке производительности необходимо отдельно учитывать:

* latency;
* throughput;
* concurrency;
* время выполнения фоновых операций.

Начальные target values:

| Операция                                   |        Target |
| -------------------------------------------------- | ------------: |
| Создание обращения                | p95 ≤ 200 ms |
| Отправка сообщения                | p95 ≤ 200 ms |
| Получение списка обращений | p95 ≤ 300 ms |
| Получение истории                  | p95 ≤ 300 ms |
| Изменение состояния              | p95 ≤ 200 ms |

Значения являются начальными архитектурными допущениями и подлежат проверке нагрузочным тестированием.

AI-операции допускают значительно большую latency и должны выполняться асинхронно там, где это необходимо.

Начальные target values:

| Операция       |    Target |
| ---------------------- | --------: |
| AI classification      |  ≤ 5 sec |
| AI summary             | ≤ 10 sec |
| AI response suggestion | ≤ 10 sec |

---

## 4.2 Масштабируемость

Система должна поддерживать горизонтальное масштабирование stateless application instances.

Архитектура должна позволять в будущем независимо масштабировать компоненты, испытывающие различную нагрузку.

Потенциальные кандидаты:

* обработка сообщений;
* AI processing;
* notifications;
* analytics/reporting.

Отдельные сервисы не должны выделяться заранее без подтверждённой архитектурной необходимости.

---

## 4.3 Доступность

Система должна продолжать работу при отказе отдельных экземпляров приложения.

Критическое состояние не должно без необходимости храниться только в памяти одного экземпляра приложения.

Отказ некритичных внешних зависимостей, таких как AI или Notification Provider, не должен приводить к недоступности основной функциональности работы с обращениями.

---

## 4.4 Надёжность

Система должна корректно обрабатывать временные сбои внешних и распределённых компонентов.

Архитектура должна предусматривать:

* retries;
* timeouts;
* idempotency;
* восстановление после ошибок;
* защиту от повторной обработки;
* graceful degradation.

Retry не должен приводить к неконтролируемому увеличению нагрузки.

---

## 4.5 Consistency и конкурентный доступ

Система должна сохранять корректное состояние обращения при конкурентном выполнении операций.

Например:

* два сотрудника не должны одновременно успешно взять одно обращение;
* конкурентные изменения состояния не должны незаметно затирать друг друга;
* сообщения не должны теряться или дублироваться из-за штатных retry и сбоев.

Конкретный механизм является архитектурным решением.

Возможные механизмы:

* database transactions;
* optimistic concurrency;
* versioning;
* locking;
* idempotency keys.

Глобально strong consistency не предполагается. Требования к consistency определяются отдельно для конкретных операций.

---

## 4.6 Порядок сообщений

Сообщения внутри одного обращения должны иметь однозначный порядок отображения.

Система должна определить правила упорядочивания сообщений при их одновременной отправке.

---

## 4.7 Ограничения

Система должна ограничивать интенсивность отдельных пользовательских операций.

Начальные допущения:

* не более 10 новых обращений от одного Customer в сутки;
* не более 1 сообщения в секунду от одного Customer;
* максимальный размер сообщения — 10 KB;
* максимальное количество сообщений в одном обращении — 1000.

Также могут применяться ограничения на:

* API requests;
* размер request/response;
* AI requests;
* частоту повторных запросов.

Точные значения являются начальными допущениями.

Ограничения должны применяться таким образом, чтобы защищать систему от чрезмерной нагрузки и неконтролируемого роста данных.

---

## 4.8 Хранение данных

История обращений должна храниться в соответствии с настраиваемой политикой retention.

Начальные допущения:

* обращения — около 3 лет;
* сообщения — около 3 лет;
* AI results — около 3 лет;
* audit information — около 1 года;
* operational metrics — около 30–90 дней в hot storage.

Значения являются архитектурными допущениями.

Архитектура должна позволять архивировать старые данные без существенного влияния на основную transactional workload.

---

## 4.9 Отчёты и аналитика

Система должна поддерживать операционные отчёты для Supervisor.

Минимальный набор:

* количество открытых обращений;
* обращения по статусам;
* обращения по категориям;
* обращения по приоритетам;
* нагрузка сотрудников;
* статистика обработки обращений;
* время обработки обращений.

Начальные target values:

| Тип отчёта                |       Target |
| ---------------------------------- | -----------: |
| Простые operational reports | p95 ≤ 2 sec |
| Сложные reports             | p95 ≤ 5 sec |

На MVP отчётность может использовать основную PostgreSQL database.

Архитектура должна позволять в дальнейшем использовать отдельную read model или analytical storage, если аналитическая нагрузка начнёт влиять на transactional workload.

# 5. Модель нагрузки

## 5.1 Основные бизнесовые допущения

Для первоначального capacity planning принимается:

| Параметр                           | Значение |
| ------------------------------------------ | ---------------: |
| Active customers/day                       |       ~1 000 000 |
| Новые обращения              |     ~100 000/day |
| Сообщений на обращение |               ~7 |
| Сообщений                         |     ~700 000/day |

Это не утверждённые бизнес-метрики, а рабочая модель для system design и load testing.

---

## 5.2 Распределение сообщений

Необходимо учитывать разные типы обращений:

| Тип           | Сообщений |
| ---------------- | -----------------: |
| Короткое |               1–3 |
| Обычное   |              4–10 |
| Длинное   |            10–30+ |

Среднее значение в 7 сообщений не должно быть единственным сценарием нагрузочного тестирования.

---

## 5.3 Write traffic

Предварительно оцениваем следующие business writes:

| Операция                                           | Примерно/day |
| ---------------------------------------------------------- | -------------------: |
| Создание обращения                        |                 100k |
| Отправка сообщения                        |                 700k |
| Изменение статуса                          |                 150k |
| Изменение категории/приоритета |                 100k |
| Assignment                                                 |                  50k |
| **Итого**                                       |  **~1.1M/day** |

Средняя нагрузка:

```text
~13 write operations/sec
```

При начальном peak factor 10×:

```text
~130 write operations/sec
```

Это предварительная оценка. Реальное количество DB operations может быть существенно выше количества HTTP writes из-за транзакций, индексов, audit events и других операций.

---

## 5.4 Read traffic

Большая часть пользовательских операций ожидается read-heavy.

Для первоначального моделирования предполагается:

```text
~8–10M read operations/day
```

Средняя нагрузка:

```text
~100 read operations/sec
```

При peak factor 10×:

```text
~1 000 read operations/sec
```

Таким образом, предварительный API capacity envelope:

| Метрика | Average |   Peak |
| -------------- | ------: | -----: |
| Read RPS       |    ~100 | ~1 000 |
| Write RPS      |     ~13 |   ~130 |
| Total RPS      |    ~113 | ~1 130 |

Это не требование «система должна выдерживать ровно 1130 RPS». Это отправная точка для capacity planning.

---

# 6. Peak и Burst

Нагрузка должна рассматриваться в нескольких режимах:

| Сценарий                     | Относительная нагрузка |
| ------------------------------------ | ------------------------------------------: |
| Средняя                       |                                         1× |
| Пиковые часы              |                                      2–3× |
| Сезонный период        |                                      3–5× |
| Кратковременный burst |                                   до 10× |

Burst-нагрузка должна использоваться для проверки поведения системы при кратковременном превышении обычной нагрузки.

Система должна использовать подходящие механизмы для сглаживания burst-нагрузки:

* очереди;
* backpressure;
* rate limiting;
* горизонтальное масштабирование;
* ограничение concurrency downstream-зависимостей.

---

# 7. Сезонность

Нагрузка системы может иметь:

* внутридневные пики;
* недельную сезонность;
* сезонные периоды;
* кратковременные события, вызывающие burst traffic.

При capacity planning необходимо учитывать не только среднюю дневную нагрузку, но и изменение:

* количества новых обращений;
* количества сообщений;
* read traffic;
* AI workload;
* notification workload.

Сезонность является фактором capacity planning, но конкретная сезонная модель должна быть уточнена позднее.

# 9. Storage Capacity Planning

Для предварительной оценки используются следующие допущения:

| Сущность |   Rows/day | Средний размер |
| ---------------- | ---------: | --------------------------: |
| Conversation     |      ~100k |                       ~1 KB |
| Message          |      ~700k |                       ~2 KB |
| Assignment       |  ~50–150k |                     ~0.5 KB |
| StatusHistory    | ~150–300k |                     ~0.5 KB |
| AIResult         |      ~300k |                       ~3 KB |
| AuditEvent       |      ~500k |                       ~1 KB |
| Notification     | ~100–300k |                     ~0.5 KB |

Значения являются очень грубой оценкой и должны быть уточнены после проектирования схемы БД.

Например:

```text
700k messages/day × 2 KB
≈ 1.4 GB/day
≈ 511 GB/year
≈ 1.5 TB / 3 years
```

Это только payload messages и не учитывает:

* PostgreSQL overhead;
* indexes;
* MVCC;
* WAL;
* replication;
* free space;
* backups.

Поэтому фактический объём PostgreSQL storage будет существенно больше.

---

# 10. Network Traffic

Для предварительной оценки принимается:

```text
Средний Message request  ≈ 1 KB
Средний Message response ≈ 2 KB
```

Тогда:

```text
700k messages/day × ~3 KB
≈ 2.1 GB/day
```

Это только traffic, связанный с отправкой сообщений.

Read traffic должен рассчитываться отдельно на основании размера API responses.

При этом размер response является отдельным архитектурным фактором, особенно для:

* списков обращений;
* истории сообщений;
* Supervisor dashboards;
* отчётов.

API не должен возвращать неограниченный объём истории одним запросом.

---

# 11. Географическое распределение

MVP работает в одном географическом регионе.

При этом архитектура не должна намеренно блокировать дальнейший переход к multi-region deployment.

Application layer должен быть максимально stateless.

Persistent и distributed state должны быть явно определены.

Multi-region deployment потенциально потребует:

* региональных экземпляров приложения;
* traffic routing;
* data replication;
* определения владельца данных;
* cross-region messaging;
* стратегии разрешения конфликтов;
* дополнительных consistency guarantees.

Multi-region deployment находится за пределами MVP.

# 12. Обоснование архитектуры MVP

## 12.1 Modular Monolith

Начальная реализация выполняется в виде **модульного монолита**.

Это осознанный выбор, а не ограничение проекта.

На начальном этапе основными неопределённостями являются:

* границы доменных модулей;
* реальные сценарии использования;
* фактический профиль нагрузки;
* характер взаимодействия компонентов;
* требования к consistency;
* точки высокой связанности.

Преждевременное разделение системы на микросервисы зафиксировало бы эти решения до появления достаточного количества данных.

Модульный монолит позволяет:

* быстро изменять доменную модель;
* выполнять операции внутри одного процесса;
* проще отлаживать систему;
* проще проводить нагрузочные эксперименты;
* избежать распределённых транзакций без необходимости;
* сохранить чёткие логические границы модулей.

При этом модули должны иметь явные границы и минимальную связанность.

В дальнейшем отдельный модуль может быть выделен в сервис, если появится конкретное обоснование:

```text
Высокая нагрузка
        ↓
Независимое масштабирование
        ↓
Выделение компонента
```

или:

```text
Сильная связанность / независимый lifecycle
        ↓
Пересмотр границы модуля
        ↓
Выделение компонента
```

---

## 12.2 Одна PostgreSQL database

На MVP используется одна PostgreSQL database.

Причины:

* на начальной нагрузке нет необходимости распределять данные между несколькими БД;
* транзакции внутри основного домена остаются простыми;
* проще обеспечить consistency;
* проще выполнять локальные запросы и аналитику;
* проще проводить эксперименты с indexes, transactions, locks и query performance;
* отсутствует необходимость в distributed transactions.

При этом схема данных и код должны избегать сильной связанности модулей на уровне БД.

В частности:

* модули должны иметь понятное владение данными;
* доступ к данным должен проходить через соответствующие границы модулей;
* cross-module SQL dependencies должны быть минимизированы;
* структура БД должна позволять в будущем разделить data ownership.

---

## 12.3 Маленькая фактическая нагрузка на старте

Функциональный MVP не обязан сразу обслуживать весь расчётный peak traffic.

Развитие системы предполагается поэтапно:

```text
Functional MVP
      ↓
Baseline performance
      ↓
Controlled load
      ↓
Increase traffic
      ↓
Find bottleneck
      ↓
Optimize
      ↓
Repeat
```

Это позволяет изучать поведение системы на каждом уровне нагрузки и не добавлять инфраструктуру до появления соответствующей проблемы.

Расчётная нагрузка используется как **target для последующих этапов**, а не как обязательная нагрузка первой версии.

---

# 13. Архитектурный задел под масштабирование

Несмотря на простоту MVP, следующие свойства должны быть заложены изначально:

### Application

* stateless application instances;
* возможность horizontal scaling;
* отсутствие критического состояния в памяти одного instance;
* явные module boundaries.

### Database

* понятное ownership данных;
* возможность partitioning больших таблиц;
* pagination вместо загрузки неограниченных наборов данных;
* возможность вынесения read workloads;
* возможность archival старых данных.

### Messaging

Архитектура не должна предполагать синхронную обработку всех операций.

Для потенциально долгих или burst-sensitive операций должны оставаться возможности использования:

* queues;
* background workers;
* Kafka;
* backpressure.

### AI

AI должен рассматриваться как потенциально медленный и ненадёжный downstream dependency.

Архитектура должна допускать:

```text
Request
   ↓
Event / Queue
   ↓
AI Worker
   ↓
AI Provider
```

вместо обязательного:

```text
HTTP Request
      ↓
      AI
      ↓
HTTP Response
```

### Future evolution

Потенциальная эволюция:

```text
Modular Monolith
      │
      ├── PostgreSQL
      │
      └── Background processing
              ↓
        Load increases
              ↓
      Identify bottleneck
              ↓
     Introduce targeted infrastructure
              ↓
       Extract components
```

Kafka, Redis, Kubernetes, отдельные БД и микросервисы добавляются только после появления конкретного архитектурного обоснования.

---

# 14. MVP Scope

MVP включает:

* создание и обработку обращений;
* сообщения;
* статусы;
* категории;
* приоритеты;
* назначение обращений;
* базовые операции Supervisor;
* базовые операционные отчёты;
* AI classification;
* AI priority suggestion;
* AI summary;
* AI response suggestion;
* уведомления;
* authentication;
* authorization;
* PostgreSQL;
* базовую observability.

Начальная реализация:

```text
Modular Monolith
        +
PostgreSQL
```

---

# 15. За пределами MVP

На начальном этапе не реализуются:

* multi-region deployment;
* active-active global architecture;
* отдельная analytical database;
* полноценный event sourcing;
* сложный workflow engine;
* многочисленные CRM-интеграции;
* сложная notification infrastructure;
* автоматическое принятие AI решений;
* преждевременное выделение каждого модуля в microservice.

---

# 16. Принцип развития архитектуры

SupportFlow развивается на основании измеряемых требований и реальных bottlenecks.

Общий цикл:

```text
Requirements
     ↓
Capacity Planning
     ↓
Domain Model
     ↓
Modular Monolith
     ↓
Baseline
     ↓
Load Test
     ↓
Measure
     ↓
Find Bottleneck
     ↓
Architectural Change
     ↓
Load Test
     ↓
Compare
     ↓
Explain
```

Основной принцип:

> **Не строить распределённую систему заранее, но проектировать MVP так, чтобы при росте нагрузки её можно было эволюционно масштабировать.**

Каждое существенное архитектурное решение должно иметь объяснение:

```text
Problem
   ↓
Constraint
   ↓
Options
   ↓
Decision
   ↓
Trade-offs
```

Такие решения фиксируются в ADR.
